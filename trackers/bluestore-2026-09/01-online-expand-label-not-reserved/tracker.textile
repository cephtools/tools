Project: bluestore | Tracker: Bug | Severity: 2 - major | Regression: 0
Subject: BlueStore: online bluefs-bdev-expand leaves new bdev label copies unreserved; object data and label overwrite each other

|Kind|data corruption / data loss (on-disk label and object data)|
|Severity|major|
|Config|default (@bluestore_bdev_label_multi=true@); needs an online expand (@ceph tell osd.N bluestore bluefs-bdev-expand@) that crosses a label position (1G/10G/100G/1000G)|
|Real-world|*Confirmed on a live OSD* (vstart, real @ceph tell osd.0 bluestore bluefs-bdev-expand@, rados writes): object unfound, PG @recovery_unfound@, HEALTH_ERR|
|Affected|main only: online expand was added by PR #66344 (merged 2026-06-30, a65fd3baf37); not in any release. Reproduced on origin/main 8e6a13e7a9a|
|Related|tracker 69997 (label locations found occupied after offline expand in NCB mode; fixed by PR 61843 via the allocator update order). The offline path reserves labels when it re-opens the store; the online path does not|

h3. Summary

The online branch of @BlueStore::expand_devices()@ writes a new copy of the bdev
label at every label position inside the grown range and appends it to
@bdev_label_valid_locations@, then hands the whole new range to the allocator with
@alloc->init_add_free()@. The label blocks are never reserved, so:

# object data can be allocated on a label block and destroy that label copy;
# a later label rewrite (@write_meta()@, another online expand) rewrites the label at that location over object data, which then reads back as EIO (csum mismatch). This window lasts until the next restart: at the next mount @_main_bdev_label_try_reserve()@ finds the location occupied and disables it (see Observed);
# possibly, with NCB, @_main_bdev_label_remove()@ at umount marks the location free in the allocation file although an object owns it (not exercised by the repro).

h3. Root cause

@src/os/bluestore/BlueStore.cc@:
* 9371-9383: label positions in @[size0, size)@ are pushed to @bdev_label_valid_locations@ and written.
* 9406-9410, online branch (@!need_to_close@): @fm->expand(); alloc->expand(); alloc->init_add_free(aligned_size0, aligned_size - aligned_size0);@ with no @init_rm_free()@ for the label blocks.
* 7020-7066: @_main_bdev_label_try_reserve()@ is only called from @_open_db_and_around()@ (8082, i.e. mount / fsck / offline expand); the online branch never calls it.

With a replicated pool the other copies would let the OSD recover the object; with size 1 (or if every copy is hit) the data is lost.

h3. Expected

The label copy at 1G stays intact, every object reads back, fsck is clean.

h3. Suggested fix

In the online branch, after @init_add_free()@, reserve each newly added label
location (@alloc->init_rm_free(loc, lsize)@), i.e. apply
@_main_bdev_label_try_reserve()@ to the new locations.
